# TF-006: Worker heartbeats and liveness visibility

## Protocol

On startup, a worker resolves one process-lifetime `instance_id` and upserts its registration. The upsert initializes `last_seen_at` with `clock_timestamp()`, re-enables an existing matching registration, refreshes its display name, and preserves its original `created_at` registration timestamp. Distinct process identities are never merged because `instance_id` remains unique.

After registration, the process starts independent claim/execution and heartbeat loops. Each scheduled heartbeat runs a narrow update matching both the worker UUID and instance identity:

```sql
UPDATE workers
SET last_seen_at = clock_timestamp()
WHERE id = $1::uuid AND instance_id = $2;
```

The existing `workers_set_updated_at` trigger also advances `updated_at`. No task row is read or locked. A missing or mismatched identity is an explicit error. A temporary failure is logged and the next scheduled tick retries; an individual operation is bounded by `WORKER_HEARTBEAT_TIMEOUT`.

SIGINT/SIGTERM cancels both loops. The process shuts down its HTTP server, waits for both goroutines, logs shutdown, and only then closes its PostgreSQL pool.

## Configuration

| Variable | Default | Rule |
| --- | --- | --- |
| `WORKER_HEARTBEAT_INTERVAL` | `5s` | Positive |
| `WORKER_STALE_AFTER` | `15s` | Greater than heartbeat interval |
| `WORKER_DEAD_AFTER` | `30s` | Greater than stale threshold |
| `WORKER_HEARTBEAT_TIMEOUT` | `2s` | Positive |

The worker and API both validate the shared interval/stale/dead contract at startup. Durations use values such as `250ms`, `5s`, or `1m`.

## Derived liveness

The API reads `statement_timestamp()` with each worker query and calculates age and state from the same reference time:

| Heartbeat age | State |
| --- | --- |
| `age <= stale_after` | `ACTIVE` |
| `stale_after < age <= dead_after` | `STALE` |
| `age > dead_after` | `DEAD` |

An existing row with no heartbeat is `DEAD` with an unknown (`null`) age. The `enabled` column retains its administrative meaning and is not overloaded with runtime liveness. Derived state cannot itself become stale in storage.

`GET /workers` and `GET /workers/{worker_id}` expose identity, display name, administrative state, lifecycle timestamps, metadata, liveness, and heartbeat age. They do not expose heartbeat configuration or database connection details.

## Database decision

No migration is required. The existing table already has `instance_id`, `created_at`, `updated_at`, `last_seen_at`, metadata, and administrative `enabled`. The unique constraint on `instance_id` supports deterministic registration and exact identity lookup. The existing partial `workers_available_idx` covers enabled-worker scans ordered by `last_seen_at`; no speculative index was added for an API that currently lists by registration time or fetches by primary key.

## Verification and limitation

PostgreSQL tests verify registration timestamps, repeated heartbeat advancement, exact-row updates, duplicate registration behavior, independent identities, and missing identities. API tests cover list/detail classification. Process tests prove heartbeats advance throughout a 900 ms handler with a 100 ms heartbeat interval, a stopped worker progresses through all three liveness states, and three workers heartbeat independently. A controlled repository failure test proves the heartbeat loop logs the failure and succeeds on a later tick.

TF-006 performs detection only. A `DEAD` worker's `RUNNING` tasks and attempts are intentionally not requeued, failed, retried, reclaimed, or otherwise modified.

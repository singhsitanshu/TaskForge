# TF-010: Durable Submission Idempotency

TF-010 makes task submission safely repeatable without changing TaskForge's at-least-once execution model.

## Logical identity

A task is one logical submitted unit of work. An attempt is one execution of that task. Retryable failures and expired-lease recovery create new attempts under the same task ID. An `Idempotency-Key` identifies a client submission, not an execution attempt.

The key is optional. A request without one always creates a new task, even when its body is identical to an earlier request. A genuinely new unit of work must use a new key or omit the key.

## HTTP contract

Clients provide the key in the `Idempotency-Key` header:

    POST /tasks
    Idempotency-Key: customer-import-7b645

The first submission returns `201 Created`. Repeating the same semantic request with the same key returns the existing task and `200 OK`, regardless of whether that task is `QUEUED`, `RUNNING`, `RETRYING`, `SUCCEEDED`, `FAILED`, or `CANCELLED`.

Reusing the key with a different semantic request returns `409 Conflict` with code `IDEMPOTENCY_KEY_REUSE`. It never changes the existing task or creates replacement work. In particular, replaying a cancelled task returns that same cancelled task.

For compatibility with the pre-TF-010 API, `idempotency_key` remains accepted in the JSON body. New clients should use the header. If both are supplied, they must match.

Keys are case-sensitive opaque identifiers over the documented ASCII set: letters, digits, `.`, `_`, `~`, `:`, `/`, `+`, `=`, and `-`. The maximum length is 255 characters. Empty values, whitespace, control characters, and other characters are rejected. Logs contain only a truncated SHA-256 key hash, never the complete key.

## Request fingerprint

The API builds a canonical JSON object containing:

- `task_type`
- `payload`
- `priority`
- `max_attempts`
- `queue`
- `scheduled_at`, represented as an optional UTC ISO-8601 timestamp with microseconds

It serializes UTF-8 JSON with recursively sorted object keys, compact separators, preserved array order, preserved Unicode code points, and non-finite numbers disabled. SHA-256 of those bytes is stored as 64 lowercase hexadecimal characters in `request_fingerprint`. Generated IDs, database timestamps, lifecycle state, results, and attempt state are excluded.

Object member order therefore does not affect identity; array order does. Visually similar but byte-distinct Unicode strings remain distinct because no Unicode normalization is applied.

## PostgreSQL arbitration

`tasks_idempotency_key_idx` is a global partial unique index over non-null keys. A keyed submission uses `INSERT ... ON CONFLICT DO NOTHING RETURNING ...` inside one transaction. The inserting request creates the task; concurrent losers load the committed winner and compare fingerprints. Matching requests replay it, while non-matching requests return `409`. A unique-key race is normal control flow and does not become a `500`.

The database constraint requires a key and fingerprint to be both null or both present for new writes. Existing installations may contain keys from the older queue-scoped, conflict-only contract. Those keys remain reserved; because no trustworthy historical request fingerprint exists, they conflict instead of being falsely treated as a verified replay. Migration aborts with an explicit error if the older database contains the same legacy key in more than one queue, because global identity would otherwise be ambiguous.

## Failure and lifecycle behavior

Task insertion, key reservation, and fingerprint persistence are the same transaction. A rollback leaves no task and no ghost key reservation. If a response is lost after commit, the client repeats the same request with the same key and receives the original task.

Retry scheduling, retry promotion, worker claims, lease renewal, completion, and expired-lease recovery do not update idempotency fields. Attempt history therefore remains naturally attached to the replayed task.

## Client timeout guidance

- If the outcome of `POST /tasks` is unknown, retry the identical request with the identical key.
- For genuinely new work, use a new key or omit the key.
- Never reuse a key while changing submission fields; TaskForge returns `409`.

## Execution guarantee boundary

TF-010 provides durable idempotency for task submission. It does not provide exactly-once execution or exactly-once external side effects. A worker may perform an external action and crash before recording success; recovery may then execute another attempt. Handlers must use destination-specific idempotency when duplicate external effects are unacceptable.

## Retention and tenancy

Keys persist for as long as their task persists. TaskForge has no delete endpoint, task-retention policy, key TTL, or automatic key cleanup. The current system is single-tenant, so keys are globally unique. A future authenticated multi-tenant design should scope uniqueness as `(tenant_id, idempotency_key)` without changing task-versus-attempt semantics.

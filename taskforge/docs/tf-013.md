# TF-013 — TaskForge Operations Console

## Status

Implemented.

## Start the console

From the repository root:

```text
cp .env.example .env
make migrate-up
make up
make health
```

Open:

- TaskForge Operations Console: <http://localhost:3000>
- API and OpenAPI documentation: <http://localhost:8000/docs>
- Grafana: <http://localhost:3001>
- Prometheus: <http://localhost:9090>

The production Nginx container proxies browser requests from `/api/*` to the Compose `api`
service. Vite's development server proxies the same path to `http://localhost:8000`, so frontend
code uses one same-origin contract in both environments. `VITE_API_BASE_URL`,
`VITE_GRAFANA_URL`, and `VITE_PROMETHEUS_URL` may override those browser-facing defaults at build
time.

For frontend-only development, first start PostgreSQL, the API, scheduler, and at least one worker,
then run:

```text
cd web
npm install
npm run dev
```

## Pages

| Route | Purpose |
| --- | --- |
| `/` | Real task-state counts, worker summary, recent tasks, and exceptional attempts |
| `/tasks` | Bounded task table with status, exact handler, and exact queue filters |
| `/tasks/:id` | Task payload/result and ordered durable attempt timeline |
| `/submit` | Real task submission with JSON and API-contract validation |
| `/workers` | Bounded workers table with backend-derived liveness |
| `/system` | Architecture, honestly reported service evidence, and observability links |

The task-ID field on `/tasks` navigates directly to the existing exact-ID endpoint. Task listing
uses offset/limit pagination with a filtered total and never downloads the entire table.

## Data and health semantics

Runtime views contain no fixture or fallback operational values. Overview task counts, recent
tasks, worker counts, and exceptional attempts come from `GET /overview`. Task detail combines
`GET /tasks/{id}` with `GET /tasks/{id}/attempts`. The worker page uses `GET /workers`.

An overview response proves the API is reachable and its PostgreSQL queries succeeded. Scheduler
health and Redis health are not exposed by the public API, so the console reports them as `Not
reported` and `Not on the execution path` rather than healthy. Worker `ACTIVE`, `STALE`, and
`DEAD` states use the backend heartbeat thresholds; JavaScript does not invent liveness rules.

Attempt cards label the PostgreSQL attempt lifecycle duration, not Go handler execution time.
Retry scheduling and lease-expiry recovery use their distinct immutable evidence fields. The UI
states that execution is at-least-once and does not imply exactly-once external side effects.

## Refresh behavior

- Overview and workers refresh every 10 seconds.
- Tasks refresh every 15 seconds.
- Non-terminal task detail refreshes every 5 seconds and stops when terminal.
- System evidence refreshes every 15 seconds.
- Every data page provides manual refresh.

Polling pauses while the page is hidden, does not overlap an active request, aborts on unmount,
and preserves the last successful snapshot when a later refresh fails.

## Task submission

The form accepts the public API fields: task type, JSON-object payload, queue, priority, maximum
attempts, and optional idempotency key. Handler input remains free text because the API/worker
registry is authoritative; the console does not advertise every benchmark or failure handler as a
production catalog. Development users may enter registered `test.*` handlers explicitly.

The UI distinguishes a newly created `201` response from an idempotent `200` replay and explains
the structured `409 IDEMPOTENCY_KEY_REUSE` conflict. Backend validation remains authoritative.

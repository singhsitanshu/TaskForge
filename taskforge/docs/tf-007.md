# TF-007: Task leases and renewal

## Purpose and protocol

A `RUNNING` task now has time-bounded ownership. Claiming atomically records `claimed_by_worker_id`, increments `attempt_count`, creates the matching `RUNNING` attempt, and sets `lease_expires_at` from PostgreSQL `clock_timestamp()` plus `WORKER_TASK_LEASE_DURATION`.

While the handler runs, a task-specific goroutine renews that lease. Renewal matches task ID, worker ID, attempt number, `RUNNING` status, and a strictly unexpired lease. It cannot create attempts or change `attempt_count`. `lease_expires_at == database time` is expired; only `lease_expires_at > database time` is renewable.

The worker uses a local confirmation deadline only as a conservative cancellation safeguard during repeated database failures. PostgreSQL remains authoritative. A transient renewal error is logged and retried on the next interval. Rejected ownership or expiration cancels the handler context, stops renewal, logs `task_lease_lost`, and skips completion.

Completion and failure lock the task and require the same task, worker, attempt, status, and valid lease. The terminal task update and attempt update are atomic. Both `SUCCEEDED` and `FAILED` clear `claimed_by_worker_id` and `lease_expires_at`. A delayed stale worker receives `ErrLeaseLost` and cannot alter either the old or a future attempt.

## Configuration

| Variable | Default | Validation |
| --- | --- | --- |
| `WORKER_TASK_LEASE_DURATION` | `30s` | Positive |
| `WORKER_TASK_LEASE_RENEW_INTERVAL` | `10s` | Positive and no more than half the duration |
| `WORKER_TASK_LEASE_RENEW_TIMEOUT` | `2s` | Positive and less than the duration |

## Schema

Migration `000004_task_leases` makes `tasks.lease_expires_at` canonical task ownership metadata. `RUNNING` requires a claimed worker and lease; every non-running state requires both to be null. It removes obsolete `tasks.leased_by_worker_id`, task lease tokens, and attempt-level lease copies. Attempts remain historical execution records identified by their UUID and `(task_id, attempt_number)`.

`tasks_running_lease_idx` supports TF-008's future expired-ownership scan:

```sql
SELECT id
FROM tasks
WHERE status = 'RUNNING'
  AND lease_expires_at <= clock_timestamp()
ORDER BY lease_expires_at;
```

Pre-TF-007 stranded `RUNNING` rows migrate to an expired lease and are not recovered.

## Heartbeat versus lease

Worker heartbeat describes process liveness. A task lease describes one attempt's ownership. They are separate loops and separate database writes. A worker can remain `ACTIVE` while a deliberately invalidated task lease is `EXPIRED`; conversely, a task lease remains valid briefly after worker heartbeat failure.

## Crash and shutdown state

SIGINT/SIGTERM cancels the handler and renewal goroutine cleanly. No shutdown requeue occurs. A hard crash stops heartbeat and renewal immediately. After time passes, PostgreSQL contains a `DEAD` worker plus a `RUNNING` task and attempt with an expired lease. That is the exact durable input intended for TF-008.

## Known limitation

Expired `RUNNING` tasks are not scanned, requeued, retried, failed, or reclaimed in TF-007.

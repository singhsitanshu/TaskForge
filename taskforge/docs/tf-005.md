# TF-005: Multi-worker atomic claiming

## Claim transaction audit

`ClaimNext` uses one connection acquired from `pgxpool` for one explicit transaction:

1. `BeginTx` starts the claim transaction.
2. A priority-ordered `SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1` locks one eligible `QUEUED` row.
3. The same transaction updates that row to `RUNNING`.
4. That update sets `attempt_count` to the selected next attempt number.
5. The same update stores `claimed_by_worker_id`.
6. The same transaction inserts the matching `RUNNING` `task_attempt`, including worker and attempt number.
7. `Commit` makes the ownership tuple durable and returns the pooled connection.
8. Every error path reaches the deferred rollback. An injected attempt-insert failure proves that the task update and attempt count do not commit independently.

No operation required to establish ownership occurs outside this transaction. `ClaimNext` returns only after commit. Handler execution begins afterward, and completion uses a separate transaction.

The claim query qualifies its ordering columns with the base-table alias. This matters because the selected task ID is returned as text; an unqualified `ORDER BY id` can bind to that text output alias and prevent PostgreSQL from using the UUID-based priority index.

## Contention harness

`worker/internal/repository/postgres_contention_test.go` creates isolated PostgreSQL schemas and uses a channel barrier to release independent goroutines simultaneously. It does not use sleeps as a concurrency mechanism.

Coverage includes:

- 20 claimers against one task for 50 iterations.
- 100/2, 500/5, 500/20, 1000/10, and 1000/20 load scenarios.
- Bounded concurrent claims across priorities 100, 50, and 10.
- Created-time and UUID tie-breaking among equal-priority tasks.
- Attempt-insert failure after the task update, followed by a successful reclaim.
- A pending handler with a second successful claim, proving claim locks are already released.
- `EXPLAIN (ANALYZE, BUFFERS)` against 20,000 eligible tasks.

`tests/test_claim_races.py` uses a test-only Go claim process. The process registers, signals readiness, and waits on stdin. A Python barrier then releases its real `ClaimNext` call alongside the FastAPI cancellation request. Every iteration must serialize to either cancellation with no attempt or a running claim with a `409` cancellation response.

## Connection pools

- The API pool is configured with `min_size=1` and `max_size=10`.
- A production worker process polls sequentially and uses `pgxpool`; a claim transaction returns its connection on commit or rollback.
- The contention test pool has `MaxConns=32`, warms 20 distinct connections before releasing the barrier, and asserts that no connections remain acquired after workloads.
- Twenty simultaneous test claimers therefore do not serialize through one connection and remain below PostgreSQL's default connection capacity in the Compose test environment.

## Query plan

The claim-supporting partial index remains:

```sql
CREATE INDEX tasks_claim_priority_idx
ON tasks (priority DESC, created_at ASC, id ASC)
WHERE status = 'QUEUED';
```

With 20,000 eligible rows, the observed plan is `Limit -> LockRows -> Index Scan using tasks_claim_priority_idx`. No additional index or schema change is warranted.

# TF-008: Expired lease recovery

## Purpose

TF-008 closes the crash-recovery gap left by renewable leases. A `RUNNING` task whose canonical task lease is expired is no longer stranded: the scheduler atomically abandons the old attempt and either requeues the task or terminally fails it when its attempt budget is exhausted.

This is ownership-failure recovery, not an ordinary application retry system. A handler that returns an error still produces `FAILED` immediately.

## Recovery protocol

Each scheduler replica runs the same context-aware loop. A scan begins immediately at startup and then runs on `SCHEDULER_RECOVERY_INTERVAL`:

1. Begin a PostgreSQL transaction.
2. Select at most `SCHEDULER_RECOVERY_BATCH_SIZE` tasks where `status = RUNNING` and `lease_expires_at <= clock_timestamp()`.
3. Order by oldest expiration and lock tasks using `FOR UPDATE SKIP LOCKED`.
4. Lock the attempt at `(task_id, attempt_count)` and validate worker, number, and `RUNNING` state.
5. Set the attempt to `ABANDONED`, set `finished_at` from database time, clear output, and set `error = lease_expired`.
6. If `attempt_count < max_attempts`, set the task to `QUEUED`; otherwise set it to `FAILED` with `max_attempts_exhausted_after_lease_expiration`.
7. Clear task owner and lease and commit both changes together.

Recovery preserves `attempt_count` and creates no row. The next ordinary worker claim produces attempt `N+1`.

## Configuration

| Variable | Default | Validation |
| --- | --- | --- |
| `SCHEDULER_RECOVERY_INTERVAL` | `5s` | Positive Go duration |
| `SCHEDULER_RECOVERY_BATCH_SIZE` | `100` | 1–10,000 |
| `SCHEDULER_RECOVERY_DB_TIMEOUT` | `2s` | Positive Go duration |

A transient database failure ends only the current scan and is retried on the next ticker event. Shutdown cancels an in-flight scan and waits for the loop to exit.

## Concurrency model

`SKIP LOCKED` distributes expired rows among independent scanners. Task status changes before commit make recovered rows ineligible for later scans. The unique `(task_id, attempt_number)` key prevents duplicate history, while the locked ownership and attempt predicates prevent a scanner from updating changed state.

No leader election, advisory global lock, Redis lock, or worker-liveness gate is used. Scheduler containers have no host-published port, so `docker compose up --scale scheduler=3` is safe.

## Transaction and corruption safety

The task and exact active attempt are both row-locked. If attempt abandonment succeeds but task transition fails, PostgreSQL rolls back the attempt update. A subsequent scan can recover the original `RUNNING` state.

If the current attempt is missing, belongs to another worker, has another number, or is not `RUNNING`, the scheduler emits `event=task_recovery_invariant_violation` and leaves the task unchanged. It does not synthesize or repair history.

## Heartbeat versus lease

Recovery reads no worker heartbeat state. An `ACTIVE` worker cannot retain an expired task, and a `DEAD` worker does not lose a still-valid task early. This preserves one ownership authority: the canonical task lease.

## Stale-owner safety

Requeue/failure clears `claimed_by_worker_id` and `lease_expires_at`. Existing TF-007 renewal and completion predicates require `RUNNING`, the same worker and attempt, and a strictly valid lease. The old worker therefore cannot renew, succeed, or fail recovered work. Once a new worker claims attempt `N+1`, the attempt-number predicate provides an additional fence.

## Observability

Scheduler JSON logs emit:

- `task_recovered` with task, old worker, attempt, expired lease, and `action=requeued`;
- `task_recovery_exhausted` with `action=failed`;
- `task_recovery_invariant_violation` with a stable reason;
- `task_recovery_scan_failed` for transient scan errors.

Empty scans are DEBUG-only.

## Verification

The PostgreSQL-backed suite proves:

- 20 simultaneous scanners recover one row exactly once over 50 iterations;
- 10 scanners recover 500 expired rows without duplicates;
- 100 valid leases remain unchanged beside 100 expired leases;
- attempts 1 and 2 requeue while attempt 3 of 3 fails;
- an injected failure after attempt update rolls the transaction back;
- missing and wrong-worker active attempts remain unchanged and are surfaced;
- three scanner replicas recover 300 rows without duplicates;
- the realistic expired scan uses `tasks_running_lease_idx`;
- a hard-killed worker's attempt 1 becomes `ABANDONED`, worker B creates attempt 2, and the task reaches `SUCCEEDED`.

## Remaining limitations

- Ordinary handler failure retry and `RETRYING` are not implemented.
- Retry backoff, delayed retries, dead-letter queues, and idempotency policy are not implemented.
- Running-task cancellation signaling is not implemented.
- Redis dispatch and schedule evaluation are not implemented.
- Recovery logs are present, but metrics and alerting are deferred.

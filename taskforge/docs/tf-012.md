# TF-012 / TF-012B — PostgreSQL-backed trusted benchmark baseline

TF-012 adds a reproducible, isolated performance suite without changing task
lifecycle semantics. The committed profiles cover noop, fixed I/O wait,
deterministic CPU work, independent API submissions, idempotency contention,
arrival-rate saturation, retries, scheduler scaling, hard-kill lease recovery,
large queues, and stability.

## Boundaries

The Go load generator is an HTTP client only. The orchestration script may
start, scale, hard-kill, and reset containers whose Compose project name begins
with `taskforge-tf012-`; it refuses any broader project name. It reads lifecycle
evidence directly from the benchmark PostgreSQL database and operational
evidence from Prometheus and Docker. Production data and non-benchmark Compose
projects are outside its scope.

Two handlers are benchmark-only predefined behavior:

- `test.noop` returns a constant successful result.
- `test.cpu` repeats SHA-256 deterministically for a validated number of
  iterations and observes cancellation.

The existing `test.sleep` supplies fixed 10, 50, and 100 ms I/O-like work. No
shell commands, dynamic code loading, arbitrary functions, or external side
effects are supported.

## Methodology

Submission throughput is the load generator's completed HTTP requests divided
by wall time. Processing throughput spans the first persisted attempt start to
the final persisted attempt finish. End-to-end throughput spans the first task
creation to the final task completion. Steady-state throughput uses the middle
80 percent of completion timestamps. These numbers are deliberately distinct.

Important scaling workloads use three trials in the baseline profile and
publish median, min, max, sample standard deviation, and coefficient of
variation. Every trial records worker/scheduler counts and all relevant lease,
poll, retry, heartbeat, recovery, and metrics intervals.

Correctness validation runs after each trial. It checks expected task and
attempt cardinality, terminal convergence, duplicate attempt numbers,
attempt-count agreement, active ownership, terminal cleanup, and recovery's
ABANDONED-attempt cardinality. Same-key API contention additionally requires
one task and one returned task ID; unique keys require one task per request.

## Interpretation

The baseline is a single-host Docker result, not a production capacity claim.
Fixed-sleep scaling indicates claim/complete transaction and polling overhead;
deterministic CPU scaling also reflects Docker Desktop CPU allocation. A retry
workload measures both worker and retry-promotion paths. Recovery throughput is
bounded by lease duration and recovery scan interval, which must always be
reported beside results.

TF-012B makes each attempt's `queue_entered_at` immutable at claim time. Retry
and recovery attempts therefore retain their own historical queue interval even
after the task row is requeued again. Raw task/attempt evidence is exported per
trial, hashed, and independently re-derived after database teardown.

Prometheus provides operator-visible bucketed observations. Trusted trials
reset isolated Prometheus storage, require exact healthy targets and fresh
boundary scrapes, calculate deltas per time-series, and invalidate resets or
unexpected target churn. Exact persisted timestamps are authoritative for
lifecycle percentiles; reconciliation preserves bucket approximation instead
of blending sources.

Publishable runs require clean committed source, image IDs, harness hashes,
three trials for every public configuration, three randomized scaling blocks,
explicit CV/drift thresholds, and recorded green regression suites. Legacy
direct scenario commands are development-only and their results are not
publishable.

Commands, profiles, raw schema, and timestamped result locations are documented
in [`benchmarks/README.md`](../benchmarks/README.md). Generated reports remain
with their machine-readable result bundle under `benchmarks/results/` and are
not committed as source.

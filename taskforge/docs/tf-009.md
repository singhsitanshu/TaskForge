# TF-009: Application retries and delayed promotion

## Semantics

TF-009 introduces ordinary handler retries without changing TF-008 crash recovery:

- `FAILED` attempt: the handler ran and returned an error.
- `ABANDONED` attempt: ownership expired before a valid result was accepted.
- Typed `RetryableError`: schedule another attempt when capacity remains.
- Ordinary error: terminalize immediately.

Unknown handlers and malformed payloads are non-retryable. No error-string parsing is used.

## Retry transaction

After a retryable handler error, the worker locks and validates current ownership and an unexpired lease. It marks the current attempt `FAILED` first, then updates the task in the same transaction. With attempts remaining, the task becomes `RETRYING`, owner and lease are cleared, `attempt_count` is preserved, `last_error` records the handler failure, and PostgreSQL calculates future `scheduled_at`. At exhaustion the task becomes terminal `FAILED` instead.

The transaction creates no attempt. Attempt `N+1` is inserted only by a later worker claim.

## Backoff and jitter

Global defaults:

| Variable | Default |
| --- | --- |
| `TASK_RETRY_BASE_DELAY` | `2s` |
| `TASK_RETRY_MAX_DELAY` | `5m` |
| `TASK_RETRY_JITTER` | `0.2` |

The retry index is zero-based: attempt 1 failure is retry index 0. Before jitter, delays are `base`, `2×base`, `4×base`, capped at `max_delay`. Jitter uses a test-injectable random unit to select a multiplier from `[1-jitter, 1+jitter]`; the final delay is capped again and never negative. Overflow-safe doubling saturates at the maximum.

## Retry promotion

The scheduler runs a second maintenance loop independent of expired-lease recovery. It scans:

```sql
WHERE status = 'RETRYING'
  AND scheduled_at <= clock_timestamp()
ORDER BY scheduled_at, id
FOR UPDATE SKIP LOCKED
```

It atomically changes due rows to `QUEUED`. `tasks_retry_due_idx (scheduled_at, id) WHERE status='RETRYING'` supports the scan. Promotion creates no attempts and does not consult worker liveness.

Promotion configuration:

| Variable | Default |
| --- | --- |
| `SCHEDULER_RETRY_PROMOTION_INTERVAL` | `1s` |
| `SCHEDULER_RETRY_PROMOTION_BATCH_SIZE` | `100` |
| `SCHEDULER_RETRY_PROMOTION_DB_TIMEOUT` | `2s` |

Multiple scheduler replicas coordinate through `SKIP LOCKED`; no leader election is required.

## Attempt limits and mixed histories

Every successful claim increments `attempt_count`, so both handler failure and crash abandonment consume capacity. Valid histories include:

    1 FAILED
    2 ABANDONED
    3 FAILED
    4 SUCCEEDED

With `max_attempts=3`, the same first three outcomes terminalize the task after attempt 3 and no attempt 4 exists.

## Cancellation

`RETRYING` is unowned waiting work, so the API now permits `RETRYING -> CANCELLED`. Cancellation is conditional and atomic, leaves the last failed attempt unchanged, and prevents scheduler promotion. `RUNNING` still returns `409`.

## Observability

Worker logs include `task_retry_scheduled`, `task_retry_exhausted`, and stale-owner rejection. Scheduler logs include `task_retry_promoted` and promotion scan failures. Empty promotion scans are DEBUG-only.

## Verification

- Backoff unit tests verify `2s, 4s, 8s, 16s, 30s, 30s`, jitter bounds, caps, and very large retry indices.
- Worker repository tests verify future database scheduling, no premature claim, exhaustion, stale-owner fencing, and injected rollback.
- Ten scanners promote 500 due retries once with no attempts created.
- A 20,000-row plan uses `tasks_retry_due_idx`.
- End-to-end retries observed approximately 100ms then 200ms before `FAILED, FAILED, SUCCEEDED`.
- Mixed end-to-end history preserves `FAILED, ABANDONED, FAILED, SUCCEEDED` and cross-cause exhaustion.

## Remaining limitations

- Retry policy is global rather than per task or task type.
- No dead-letter queue or administrative retry override.
- No recurring/cron scheduling or Redis dispatch.
- No running-task cancellation signaling.
- No retry metrics or alerting.

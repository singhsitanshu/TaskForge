# TF-011 observability contract

## Architecture

Each API, worker, and scheduler process owns a private Prometheus registry and exposes it at `GET /metrics`. Prometheus scrapes API by stable service name and discovers all worker and scheduler replica addresses with Compose DNS service discovery. Grafana reads Prometheus and is provisioned from version-controlled files.

Business-event metrics are recorded only after the corresponding durable transition succeeds. A failed Prometheus observation cannot affect a PostgreSQL transaction or task processing. The scheduler also samples aggregate PostgreSQL state every `SCHEDULER_METRICS_INTERVAL`; a failed sample increments an error counter and retains the previous gauge values.

Every scheduler replica emits the same sampled global gauges. This avoids a singleton and preserves failover, but queries must use `max`, never `sum`, across scheduler replicas. Event metrics remain process-local and are summed across replicas.

## Labels and cardinality

| Metric family | Labels | Cardinality rationale |
| --- | --- | --- |
| API requests | `method`, `route`, `status_class` | Methods and status classes are finite; routes use templates such as `/tasks/{task_id}`, never raw URLs |
| API duration | `method`, `route` | Same bounded route templates |
| Submissions | `outcome` | Exactly `created`, `replayed`, `idempotency_conflict` |
| Cancellations | `outcome` | Exactly `cancelled`, `already_cancelled`, `conflict`, `not_found` |
| Worker completion | `outcome` | Exactly `success`, `terminal_failure`, `retryable_failure` |
| Attempts | `outcome` | Exactly `succeeded`, `failed`, `abandoned` across distinct owners |
| Heartbeats | `outcome` | Exactly `success`, `error` |
| Lease renewals | `outcome` | Exactly `success`, `error`, `lost` |
| Recoveries | `outcome` | Exactly `requeued`, `exhausted` |
| Task state | `status` | Seven database enum states |
| Worker state | `liveness` | Exactly `ACTIVE`, `STALE`, `DEAD` |
| All other TaskForge metrics | None | One series per process/target |

Task IDs, attempt IDs, worker IDs, instance IDs, idempotency keys, payload values, error strings, IPs, and raw URLs are forbidden as labels. `task_type` is intentionally omitted even though current handlers are allowlisted, because the public submission field accepts arbitrary values.

## Latency definitions and buckets

`queued_at` is initialized on submission and reset only when recovery or retry promotion returns a task to `QUEUED`. Claim reads it in the claim transaction. Queue wait is `attempt.started_at - task.queued_at`; `scheduled_at` retains its dispatch/retry-due meaning.

Recovery lag is observation time minus the expired `lease_expires_at`. Retry lateness is observation time minus `scheduled_at`. Negative durations are clamped to zero only at the metric boundary to tolerate clock precision artifacts.

Total task latency is the durable terminal `completed_at - created_at`. API cancellation, normal worker completion, retry exhaustion, and recovery exhaustion each observe only their successful terminal transition. Worker and scheduler repository code returns PostgreSQL's transition timestamp, avoiding local-clock approximations.

Short database/API histograms use buckets from 1–5 ms through 5 seconds. Task-duration histograms range from 10 ms through one hour. Scheduler lag histograms range from 10 ms through 15 minutes. These cover fast tests and production work without excessively dense series.

## Aggregate gauge semantics

The scheduler sampler queries PostgreSQL for task statuses, worker liveness, running attempts, claim-eligible tasks, and expired leases. `ACTIVE`, `STALE`, and `DEAD` use the same configured thresholds as the API: age below `WORKER_STALE_AFTER`, age at/above stale, and age at/above `WORKER_DEAD_AFTER` (including never-seen workers), respectively.

Samples are eventually consistent across their three bounded queries. Every successful sample replaces every bounded status/liveness series, including zeros. A sample failure leaves the last values intact and exposes the failure and last-success timestamp.

## Prometheus and Grafana

Prometheus configuration is in `monitoring/prometheus/prometheus.yml`. Worker and scheduler jobs use DNS A-record discovery so scaling does not require configuration edits. Expected target jobs are `taskforge-api`, `taskforge-worker`, and `taskforge-scheduler`.

Grafana automatically provisions datasource UID `taskforge-prometheus` and dashboard UID `taskforge-operations`. The dashboard contains Overview, Latency, Reliability, Workers, and API sections. Histogram panels use `histogram_quantile` over `rate(..._bucket[5m])`; event rates sum replicas, while database gauge panels use `max` to avoid replica multiplication. Ratios use `clamp_min` for safe empty windows.

## Health and readiness

| Service | `/healthz` | `/readyz` |
| --- | --- | --- |
| API | Process/router alive | Bounded PostgreSQL `SELECT 1` succeeds |
| Worker | Process/server alive | Registration completed at startup and bounded PostgreSQL ping succeeds; idle is ready |
| Scheduler | Process/server alive | Maintenance service initialized and bounded PostgreSQL ping succeeds; no pending work is still ready |

Database outages do not make liveness fail. Prometheus `/-/healthy` and Grafana `/api/health` remain their own service health checks.

## Correctness boundary

Metrics do not claim exactly-once task execution. TaskForge remains at-least-once: a handler can produce an external side effect and crash before durable success. Idempotent submission creates one logical task per valid key, while external side-effect deduplication remains the handler or destination's responsibility.
